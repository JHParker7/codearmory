This chart deploys only the CORE services (gatekeeper, registry, conductor, builder,
portal). Every other service (blueprints, forge, workflows, tickets, hooks, containers,
notifications, outpost-gateway, chaos, argo, gitea) is enabled and deployed at runtime
by the builder service — during first-run setup or later in settings. When you enable a
non-core service you supply its connection config (db_url, redis_url, and any required
credentials); builder registers it with the registry, provisions its secrets, and brings
up its workload + infra.

Service keys (gatekeeperServiceKey, conductorForwardKey, etc.) are auto-generated on
first install and preserved across upgrades. No manual key generation is required.

IMPORTANT — fresh install only:
  The core cross-service keys (gatekeeper-services, conductor-forward-key, registry
  service-accounts/admin-accounts) are assembled by reading sibling secrets at render
  time. On a brand-new install those secrets do not yet exist, so the first install can
  produce mismatched keys. Fix this with a one-time second apply:

    helm upgrade {{ .Release.Name }} <chart> -n {{ .Release.Namespace }}

  Subsequent upgrades sync correctly without it.

Before production use, make sure you have set:
  - gatekeeper.secret.oidcSigningKey              (stable ECDSA key; ephemeral if unset)
  - postgresql.auth.postgresPassword              (optional — auto-generated when empty)

  Non-core service config (e.g. containers' registry URL, gitea URL + token) is supplied
  when you enable that service via builder, not in this chart's values.
